● Plan written to IMPLEMENTATION_PLAN_M13.md. Summary of what's in it:

  Two new bugs found while tracing the ACK chain

  Beyond the five root causes we already discussed, tracing action_sink turned
  up two more real bugs:

  Actions replay within one run. collect() (action_sink.py:99) returns the
  bucket and never clears it. reset() runs only at the start of run_stream
  (agent_loop.py:454). So in a two-step run — step 1 opens YouTube, step 2
  searches — the step-2 emission at agent_loop.py:586 yields both, and the
  browser opens YouTube a second time.

  One ACK covers many actions. attach_dispatch overwrites b["_meta"] on each
  call, so only the last action's action_id survives. Earlier frontend actions
  in the same run could never be acknowledged — permanent UNKNOWN even after
  fixing register_dispatch.

  Both fixed by draining the sink per action instead of per run.

  Structure

  Phase 1 — Truthfulness. Four bug fixes, each independently testable, no
  redesign:
  1. Wire register_dispatch at execution/coordinator.py:87 (attach_dispatch must
  return the id it mints — currently it's discarded)
  2. Sink isolation (the two bugs above)
  3. No-op gate at agent_loop.py:505 — action turn with zero tool calls gets one
  nudge, then an honest failure, never "Done."
  4. wait_for_verdict() on Phase 4 + verify-before-speak, bounded at 3s → retry
  once on FAIL → admit

  Phase 2 — Understanding. One resolver call per turn replacing classify_primary
  (cost-neutral, it substitutes for a call that already happens). Emits a
  self-contained goal plus kind / self_contained / refers_to_previous /
  is_confirmation / unresolved. Then ~150 lines of language-guessing deleted,
  including brain_service.py entirely. Turn 6 sends "search for Ishq by Fahim 
  Abdullah", never "it".

  Two independent guards against turn 3 recurring: the resolver understands the
  reference, and a state-based rule — last verdict FAIL/UNKNOWN +
  refers_to_previous ⇒ the chat route is not permitted. That one is a state
  check, so it holds even if the resolver misjudges.

  Things worth your attention before I start

  - Shadow mode for the resolver (step 6): it runs and logs but isn't obeyed for
  one session's worth of real use, so you can see what it would have understood
  before it drives anything.
  - Every turn shows "Understood: …" in the Activity panel. That's the
  mitigation for a confidently-wrong resolution — you see the misunderstanding
  rather than just the wrong outcome.
  - Deleting _rule_based_primary means no LLM ⇒ no routing. Verified cache
  entries still replay offline; everything else becomes an honest error. This
  follows from your "kuch bhi hardcoded nahi" — flagging it because it's the one
  place the plan makes a failure mode worse on purpose.
  - Nine flags added, all defaulting on, all revertible without a code change.
